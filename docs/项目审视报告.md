## 2. 合理之处（保持，别动）

1. **目录结构**：`sites/<code>/` 按站点、`global/` 全局、`_templates/` 模板——正好对应"多站点、多类型、有共用资源"的现实，且 `_templates` 放在 sync 作用域外是正确决策。
2. **全量 sync + 红线**：针对 ADC"全量对账会删资源"的模型，用"永远全量 glob + 严禁 `configs/**/*.yaml` + diff 无 delete 才准"守住，方向正确。
3. **sync 留人工**：AI/脚本默认不 sync、diff 后 YES 确认——对写网关的操作是正确姿态。
4. **AGENTS.md + AI 指引 + 官方文档镜像**：让 AI 可持续、合规地写配置，且字段以官方为准不猜——这是本仓库最大的长期价值。
5. **证书三方案 + 轮换手册 + 私钥不入库选项**：覆盖了运维最频繁的证书场景。
6. **可读性规范**：字段顺序/注释/最小 diff——保障"人审人改"。

## 3. 弊端与缺陷（按严重度）

### P0 / P1（建议立即处理）

**P1-1 无 git 仓库（最高风险）**
- 证据：仓库无 `.git`；但 `ADC使用指南.md:531`、`证书轮换操作手册.md:76`、`配置仓库结构设计.md:306` 的回滚/历史方案都依赖 `git revert`/Git 历史。
- 后果：无历史、无回滚、无协作基础；任何一个文件丢失/误改都不可追溯（本会话已发生过测试站点文件被删的事件）。
- 处置：**立即 `git init` + 首次提交**；`.gitignore` 已就绪（忽略 `.bin/`、`.env`、`diff.yaml`）。

**P1-2 首次 sync 从未执行，管线未经过真实网关验证**
- 证据：`dump` 显示网关为空；`diff` 从未产生过真实变更；`sites/` 目前为空（唯一的测试站点已删）。
- 后果：lint/validate/diff 通过 ≠ 网关真实行为正确（上游可达性、TLS、插件默认值等只有真机才知道）。
- 处置：建仓后，用**一个小流量/测试站点**完整走一遍 `lint → validate → diff → sync → curl 验证`，验证管线后再上正式站点。

**P1-3 工具不进仓库（.bin/ 被忽略），新环境无法自举**
- 证据：`.gitignore` 忽略 `.bin/`；`adc.cmd` 依赖 `.bin\adc\adc.exe`。
- 后果：克隆/新机器没有 adc.exe，`adc.cmd` 直接失效；无自动化安装步骤。
- 处置：新增 `scripts/install-adc.ps1`（从 GitHub releases 下载对应平台 zip 解压到 `.bin/`，校验版本），并写进 README 的"首次使用"。

**P1-4 缺 `.env.example`，新克隆不知道如何连接**
- 证据：`.env` 被忽略但仓库无示例模板。
- 后果：新成员/新环境无从知道要配 `ADC_BACKEND/SERVER/TOKEN`。
- 处置：新增 `.env.example`（占位值 + 注释），README 说明"复制为 `.env` 后填写"。

### P2（重要，尽快补）

**P2-5 「一个站点 = 一个 service」是隐含假设，文档未明示**
- 现状：模板都是一个 service；设计写"每站一个 `service.yaml`"。
- 弊端：一个站点往往有多个后端服务（官网 web + api + 静态），需要多个 service——现在只能塞进一个 service 的多条 route（共用上游）或靠"一个域名拆多个站点"迁就。
- 处置：设计文档明确"一个站点目录可含多个 service 文件：`service.yaml`、`service-api.yaml`、`service-static.yaml`"，并给出多 service 站点示例。

**P2-6 空资源文件的"所有权声明"有隐性风险**
- 现状：`global/consumers/internal.yaml`、`partner.yaml`、`ssls/wildcard.yaml`、`global-rules.yaml` 都是**空集合**（`consumers: []` 等）。
- 弊端：这些文件在 sync 作用域内，意味着"仓库独占消费者/证书/全局规则"——**任何通过 Dashboard/Admin API 手工创建的资源，下次 sync 会被删除**。当前网关为空所以无碍，但团队一旦有人用 Dashboard 调试就会被误删。
- 处置：二选一——(a) 明确这是"从第一天起仓库全量接管"的约定，写进 README 红线；(b) 或这些文件在真正有内容前不放进作用域（用 `--include-resource-type` 圈定当前需要管理的类型）。建议选 (a) 并加一条显式警告。

**P2-7 模板占位符能通过 lint（潜在误同步源）**
- 证据：`_templates/*.yaml` 显式 lint 全部通过（占位符是合法字符串）。
- 弊端：一旦有人误用 `configs/**/*.yaml` 把模板纳入 sync，会以占位名创建垃圾资源；目前仅靠纪律防护。
- 处置：脚本加一道守卫——`lint/diff/sync` 前校验文件列表里不含 `_templates/`（命中即报错退出）。

**P2-8 无 CI，且脚本是 Windows/PowerShell 专属**
- 现状：设计第 11 节有 CI 方案但未落地；`scripts/*.ps1` 依赖 PowerShell 和 `.\adc.cmd`。
- 弊端：Linux 上的 GitHub Actions/GitLab CI 需要 sh 版本或容器内 PowerShell；在 git 建仓前 CI 也无从谈起。
- 处置：建仓后按第 11 节落地 CI；若 CI 跑 Linux，给脚本配 `scripts/*.sh` 或统一用容器（含 node/adc 的镜像）。

**P2-9 文档与现实的零散不一致**
- 证据：`ADC使用指南.md:56` 提到"仓库里可能拉了 node_modules 开发依赖"（实际不存在）；回滚步骤依赖 git（无 git）；`docs.api7.ai/enterprise/*` 归档链接仍作为主参考。
- 处置：同步修正这几处；归档链接改为"保留说明 + GitHub 实时文档为主"。

### P3（低优先级/可选）

**P3-10 中文文件名**：`docs/官方文档资料库.md` 等中文文件名在部分 CI/工具/URL 场景有兼容风险（Git 本身支持 UTF-8 文件名，团队一致即可）。可选：统一英文文件名 + 中文 title。
**P3-11 无备份/恢复演练**：`adc dump --with-id` 的基线备份、以及"从基线恢复网关"的演练未做；建议定期 `dump` 留档并演练一次恢复。
**P3-12 `.env` 明文 Token**：目前可接受（已 gitignore）；后续可演进到 Windows 凭据管理器/环境变量注入。
**P3-13 多环境未落地**：单 `.env` 单网关；将来 dev/staging/prod 需按设计第 9 节拆分（文件 + 标签 env，或目录/分支级拆分）。

## 4. 日后使用好不好？（前瞻）

**好的方面**
- 新站点上线 = 复制模板改占位符 → 走一遍脚本 → sync，规范化且快。
- AI 可持续按规范写配置，人只审 diff；可读性规范让审查负担小。
- 证书轮换有手册、私钥可不入库；官方文档离线可查。
- 多团队可用 `--label-selector` 分区，防互相误删。

**真正的考验点**
1. **第一个真实站点的首次 sync** —— 这是整条管线第一次接受真实网关检验（上游可达、TLS、插件默认值）。
2. **团队纪律** —— 空资源所有权声明 + "sync 全量" 两条，靠约定执行；无人违反时很安全，一旦有人手工改 Dashboard 就被抹。CI + 守卫脚本能显著降低风险。
3. **工具与环境的自举** —— git init、.env.example、install 脚本补上后，新环境才能在 10 分钟内跑起来。
