## 1. 设计目标与根本约束

### 1.1 设计目标

| 目标 | 手段 |
| ---- | ---- |
| 站点很多（几十~上百） | 每站点一个目录，作为**最小变更单元**：新增/修改/回滚都只动一个目录 |
| 类型很多（官网/API/WS/静态/后台/对外接口…） | **目录按站点、类型用标签**，双维度不打架；每种类型提供**可复制的模板** |
| 多人/多团队维护不互相误删 | 强制 `labels.owner` + `--label-selector` 分区（官方推荐做法） |
| 可审计、可回滚 | 站点代码、命名、标签全部规范化；一切走 YAML + `sync`，禁手工 Admin API |
| 可检索 | 站点代码、`site_type` 等标签支持 `dump`/`diff` 按维度盘点 |

### 1.2 根本约束（来自官方文档，写任何结构前必须记住）

1. **`adc sync` 是全量对账（reconciliation）**：命令作用域内、本地文件里没有的远端资源会被**删除**。
   → 每次 `sync` 必须把**全部**配置文件一次性传入（用 glob），或严格用 `--label-selector` 圈定自己负责的部分。
   （出处：[adc/configuration.md](./official/adc/configuration.md) 结构说明、[adc/workflow.md](./official/adc/workflow.md)）
2. **资源 ID 由名字生成**：`service = sha1(name)`、`route = sha1(<service>.<route>)`、`consumer = username`、`ssl = sha1(snis.join(','))`。
   → **改名 = 删旧建新**，会造成流量中断；接管存量资源必须 `dump --with-id`。
   （出处：[adc/resource-ids.md](./official/adc/resource-ids.md)）
3. **`global_rules` / `plugin_metadata` 是全网关作用域且不受 label 过滤** → 单独文件、改动必须全员审慎。
   （出处：[adc/label-selector.md](./official/adc/label-selector.md)）
4. 字段合法性以 **schema 为准**：`adc lint` 按 [adc/schema.json](./official/adc/schema.json) 校验；插件参数查 [apisix/plugins/](./official/apisix/plugins/)。

## 3. 命名规范

### 3.1 站点代码 `site-code`

- 取值：站点**主域名去掉 `www.`/`m.` 后的部分**，全小写、只含字母数字连字符。
  例：`www.ynfwyy.com` → `ynfwyy`；`mall.example.com` → `mall`。
- 唯一性：全仓库唯一；既是目录名、又是标签 `site` 的值、又作为资源名前缀。

### 3.2 文件与资源命名

| 对象 | 规范 | 示例 |
| ---- | ---- | ---- |
| 站点目录 | `<site-code>/` | `ynfwyy/` |
| 站点文件 | `service.yaml` / `ssl.yaml` / `consumers.yaml`（固定名，便于工具与人类查找） | — |
| `service.name` | `<site-code>-<用途>`（全局唯一） | `ynfwyy-www`、`mall-api` |
| `route.name` | `<site-code>-<路径/用途>`（service 内唯一） | `ynfwyy-root`、`mall-order-v1` |
| `consumer.username` | `<site-code>-<用途>`（全局唯一） | `ynfwyy-member`、`internal-scm` |
| `credential.name` | 同 consumer 下唯一即可 | `primary-key` |
| 通配证书文件 | `wildcard.yaml`，`snis` 写明覆盖域 | — |

### 3.3 强制标签（每个 service / consumer / ssl 都打）

```yaml
labels:
  site: ynfwyy          # 站点代码（必填）
  site_type: www        # 类型（必填，枚举见 4.1）
  env: prod             # 环境：prod / staging / dev
  owner: team-ops       # 负责团队（必填；多团队分区依据）
  contact: ops@example.com   # 责任人（建议）
```

## 4. 标签体系（类型维度）与分区管理

### 4.1 站点类型 `site_type`（与目录解耦，用标签表达）

| site_type | 适用 | 典型特征 |
| ---- | ---- | ---- |
| `www` | 官网/门户 | hosts 全域名、`uris: [/*]`、方法全开、常开 WebSocket |
| `api` | API 服务 | 路径前缀 `/api/*`、认证插件、严格限流 |
| `ws` | WebSocket/长连接 | `enable_websocket: true`、upstream 超时调大 |
| `static` | 静态资源/文件 | proxy-cache、gzip、长缓存 |
| `admin` | 管理后台 | IP 白名单、basic-auth/SSO、仅内网 |
| `partner` | 对外合作接口 | key-auth + 限流 + 审计日志（http-logger） |
| `internal` | 内部系统 | 通常不打公网，走内部认证 |

> 目录里**不要**再按类型建一层（如 `sites/api/...`），避免双重分类造成一个站点难以归属；
> 类型只作为标签存在，支持 `--label-selector site_type=api` 全量盘点。

### 4.2 多团队分区（防误删的官方方案）

```powershell
# 团队 A 只同步自己负责的站点（标签自动注入，见官方 label-selector 指南）
.\adc.cmd sync -f configs\sites\mall\service.yaml --label-selector owner=team-a

# 盘点某个类型的所有站点
.\adc.cmd dump -o api-sites.yaml --label-selector site_type=api
```

要点（出处：[adc/label-selector.md](./official/adc/label-selector.md)）：
- 标签精确匹配，多标签 AND 组合；**没有**通配符/OR。
- `--label-selector` 会把标签自动注入本地资源并过滤远端，保证多次 sync 稳定。
- `global_rules` / `plugin_metadata` 不受标签过滤 → **永远全员一起管理，不要用 selector 碰它们**。

## 5. 各资源「放哪」速查

| 资源 | 放置 | 说明 |
| ---- | ---- | ---- |
| `services:`（含 routes/upstream） | `configs/sites/<code>/service.yaml` | 每站一个；一个 service 内可多个 routes 共享上游/插件 |
| `ssls:` | 见 [5.1 SSL 证书：放哪、怎么换、私钥放哪](#51-ssl-证书放哪怎么换私钥放哪) | ssl 的 `snis` 决定绑定域；资源 ID = `sha1(snis)` |
| `consumers:` | 公共调用方 → `configs/global/consumers/`；站点专属 → 站点目录 `consumers.yaml` | username 全局唯一 |
| `global_rules:` | `configs/global/global-rules.yaml` | 全网关生效，改动需全员确认 |
| `plugin_metadata:` | `configs/global/plugin-metadata.yaml` | 同上 |
| 多上游/灰度 | **首选 `traffic-split` 插件**（官方文档完整：[traffic-split.md](./official/apisix/plugins/traffic-split.md)）；`services[].upstreams` 数组仅在 [schema.json](./official/adc/schema.json) 中出现，官方 configuration.md 未记录语义，**落地前先实测**再采用 | 见 schema.json / traffic-split.md |

### 5.1 SSL 证书：放哪、怎么换、私钥放哪

**放置规则（一张证书只在一个文件里定义一次）**

| 场景 | 放哪 | 说明 |
| ---- | ---- | ---- |
| 站点独有证书（该站域名专用） | `configs/sites/<code>/ssl.yaml` | `snis` 填该站域名 |
| 通配证书（`*.example.com` 覆盖多子域） | `configs/global/ssls/wildcard.yaml` | 一个通配证书管多个子站 |
| 多站点共用一张多 SAN 证书 | `configs/global/ssls/shared-<名称>.yaml` | 跨站共用，**只定义一次** |

> 关键机制：SSL 资源 ID = `sha1(snis 按逗号连接)`（出处：[resource-ids.md](./official/adc/resource-ids.md)）。
> - **同一组 `snis` 的证书只允许出现在一个文件里**，否则 ID 冲突。
> - **轮换证书时保持 `snis` 不变** → ID 不变 → sync 是原地更新（update），不会删旧建新、不中断 TLS。

**轮换工作流（定期更换证书）**

```powershell
# ① 拿到新证书（fullchain + 私钥），替换 ssl.yaml 中 certificate/key（或更新 secret/env，见下方方案表）
# ② 校验 + 看差异：必须只出现 update/create，绝不能出现 delete
.\scripts\lint.ps1
.\scripts\diff.ps1
# ③ 确认后同步
.\scripts\sync.ps1
# ④ 验证线上证书已生效
openssl s_client -connect <域名>:443 -servername <域名> </dev/null 2>/dev/null | openssl x509 -noout -subject -dates -fingerprint
```

> 建议：证书到期前 1~2 周轮换；用 `openssl x509 -enddate -noout -in cert.pem` 查到期日，配日历/监控提醒。

**私钥放哪（三档方案，按安全级别递进）**

| 方案 | 写法 | 优点 | 代价 | 适用 |
| ---- | ---- | ---- | ---- | ---- |
| A 内联入库（默认） | `certificate:`/`key:` 直接写在 yaml | 最简单，纯 GitOps | 私钥进 Git 历史；仓库必须私有 + 限权 | 普通站点起步 |
| B 环境变量引用 | `certificate: "$env://SSL_CERT"` / `key: "$env://SSL_KEY"` | 私钥不入库 | 每台网关节点都要配 env，多节点需一致；轮换改节点配置 | 核心站点 |
| C Secret 管理器 | `certificate: "$secret://vault/1/<名称>/cert"` / `key: "$secret://vault/1/<名称>/key"` | 集中管理、审计、可自动轮换 | 需部署 Vault / AWS SM / GCP SM 并配置 Secret 资源 | 高安全 / 规模化 |

出处：[apisix/terminology/secret.md](./official/apisix/terminology/secret.md)（引用格式 `$secret://$manager/$id/$secret_name/$key`）、
[admin-api.md §SSL](./official/apisix/admin-api.md)（cert/key 字段支持 Secret 引用）。

> ⚠️ 官方提示的两个坑（[secret.md](./official/apisix/terminology/secret.md)）：
> 1. 字段用 `$secret://` / `$env://` 引用后，**schema 校验（minLength/pattern 等）会被跳过**——必须确保引用可解析，
>    否则字面引用串会被当作值使用并写入错误日志。
> 2. 内联 PEM 有长度约束（certificate ≥128 字符、key ≥32 字符），且格式必须完整（含 `-----BEGIN/END-----` 行）。

模板见 [`configs/_templates/ssl.yaml`](../configs/_templates/ssl.yaml)（内联版 + `$env://` 版两个示例）。
轮换操作手册见 [`docs/证书轮换操作手册.md`](./证书轮换操作手册.md)。

### 5.2 插件作用域与路由颗粒度（站点差异怎么表达）

**结论先行：站点间插件/路由差异不需要改目录结构**——差异靠「插件挂在哪一层」+「路由拆多细」两个旋钮表达，
全部落在 `sites/<code>/service.yaml` 一个文件里（service 级 `plugins` + `routes[]` 各自 `plugins`）。

**插件作用域层级（官方 plugin.md 合并优先级，从高到低）**

```
Consumer  >  Consumer Group  >  Route  >  Plugin Config  >  Service
（global_rules 是独立通道，与本地同名插件【都执行】，不是覆盖）
```

| 挂在哪 | 放什么 | 说明 |
| ---- | ---- | ---- |
| `global_rules` | 全网关基础（监控埋点、通用日志） | 改动影响所有站点；与本地同名插件**两个实例都执行** |
| service 级 `plugins` | 该站全站通用（CORS、全站限流） | 该 service 所有 route 共享 |
| route 级 `plugins` | 该路由特有（`/api/*` 挂 key-auth、`/static/*` 挂 proxy-cache） | 合并时**覆盖** service 级同名插件 |
| consumer 级 `plugins` | 按调用方（认证后个性化） | 优先级最高 |
| `_meta.priority` | 同阶段插件执行顺序（越大越先） | 默认优先级见各插件文档 |

> 关键误区：global_rules 里挂过的插件，route 里再挂**不会覆盖**，而是两个实例都执行（官方 plugin.md 原文）。
> "全站都要"放 global_rules，"只某些路由要"放 route 级，不要指望 route 覆盖 global。

**路由颗粒度（一个 service 下 N 条 route，粗细可混）**

- 匹配规则（官方 router.md）：默认 `radixtree_host_uri`（host+uri 匹配）；**精确匹配优先于前缀/通配**（自动）；
  同 uri 命中多条时比 route 的 `priority`（越大越先）。
- 颗粒度决策准则 = **差异点在哪**：
  - 差异按路径/方法/域名区分 → 拆多条 route 各挂插件（如 `/api/*` 认证限流、`/ws/*` 只开 websocket、`/*` 兜底）
  - 全站一致 → 一条粗路由（`/*`）+ service 级插件
- 推荐「具体路由 + 兜底路由」模式：具体路径路由写前面，兜底 `/*` 放最后、priority 最低（精确匹配天然优先）。
- 与 sync 的关系：路由是独立资源，ID = `sha1(service.route)`；增删/改名路由都会在 diff 中体现（**改名 = 删旧建新**）。
- 插件热加载：改插件参数无需重启网关（官方 plugin.md 末尾）。

**跨站点复用同一套插件组合（多个 API 站都用 key-auth + limit-count 同参数）**

> ⚠️ 官方 `plugin_config` 资源可跨路由共享插件，但 **ADC 声明式 YAML 无法声明 plugin_config**
> （schema.json 顶层只有 services/ssls/consumers/consumer_groups/global_rules/plugin_metadata，已核实）。备选：

1. **复制到各站点（默认）**：各自 `service.yaml` 里写一遍，简单、可独立演化（参数分叉也没问题）；
2. **service 级插件**：同站多路由共享；
3. **consumer_groups**：按消费者组挂公共插件；
4. **模板承载默认值**：`_templates/api.yaml` 即"API 站点插件默认组合"，新站复制后按需增删。

> 站点 `site_type` 标签只是**分类维度**，不代表插件集合固定——同类型站点的插件仍可各不相同。

### 5.3 可读性与可维护性规范（人读、人审、人改）

配置文件的最终读者是**人**（审查、排障、手动修改）。AI 写的每一份 YAML 都必须做到：
**不看文档也能读懂每个字段；改动最小化，方便 diff 审查。**

**字段顺序（全仓库统一，模板已按此排）**

```
service:  name → description → labels → upstream → routes
route:    name → uris → hosts → methods → priority → enable_websocket → plugins
upstream: type → scheme → pass_host → nodes → checks → timeout
plugins:  键按字母序
```

顺序固定后，人扫文件能快速定位字段，diff 也更好对比。

**注释规范**

| 位置 | 注释什么 | 示例 |
| ---- | ---- | ---- |
| 文件头部块 | 站点身份、负责人、后端、类型（人看的第一眼） | `# 站点：mall（商城）｜ 负责人：team-b ｜ 后端：10.0.0.11:8080` |
| 行内 | 只注释"不显然"的值：业务含义、为什么这样 | `count: 600   # 每 IP 每分钟 600 次（线上峰值 ~400）` |
| 分区 | routes 多时按业务分段 | `# ---- 前台路由 ----` `# ---- 管理路由 ----` |

- 不注释显而易见的内容（`name:`、`uris:` 不需要解释）。
- 优先注释**为什么**（`verify: false  # 上游是 http，无 TLS`），而不是**是什么**。

**YAML 语法约定（可读性优先）**

| 规则 | 说明 |
| ---- | ---- |
| 2 空格缩进 | 禁用 tab |
| 短数组内联、长数组列表 | `methods: [GET, POST]`；超过 4 项或需注释时用 `- item` 列表 |
| 字符串建议加引号 | 含 `: # { } [ ]` 等特殊字符**必须**引号；中文建议引号 |
| 布尔 `true/false`、数字裸写 | 不加引号 |
| PEM 证书 | 用 `\|` 块状（见 `_templates/ssl.yaml`） |

**可维护性约定**

1. **一个站点一个 `service.yaml`**，单文件尽量 ≤ 200 行；routes 太多时用分区注释组织（ADC 的 routes 必须在 service 内，无法拆文件）。
2. **最小 diff**：一次改动只改一件事；不顺手重排、不顺手改名、不顺手"美化"无关部分——diff 越小越易审。
3. **删除即删除**，不留大段注释掉的旧配置（Git 历史可回看；本仓库建仓后生效）。
4. **站点 `README.md` 维护变更记录**：`日期 / 内容 / 原因` 三列，作为人工维护日志。
5. **labels 的 `owner`/`contact` 必填**——人出了问题能找到负责人。
6. **模板是范本**：站点文件应与模板同构（字段顺序、注释风格一致），方便与模板比对、也方便新人上手。
7. **魔法值必须注释**：限流阈值、超时秒数、priority、`verify: false` 这类，旁边写明业务依据。

## 7. 日常工作流

### 7.1 新增一个站点（标准流程）

```powershell
# ① 复制模板（模板在 configs/_templates/，不在 sync 作用域内）
Copy-Item configs/_templates/api.yaml configs/sites/mall/service.yaml
#    改 <site-code>、域名、后端地址、labels；需要证书/消费者则再加 ssl.yaml / consumers.yaml

# ② 本地校验（不联网）
.\scripts\lint.ps1

# ③ 后端校验（更严）
.\scripts\validate.ps1

# ④ 看差异：只应有「新增」，绝不允许出现无关的「删除」
.\scripts\diff.ps1

# ⑤ 确认后全量同步
.\scripts\sync.ps1
```

### 7.2 脚本封装（`scripts/*.ps1`，落地时创建）

所有脚本先 `Set-Location "$PSScriptRoot\.."` 锚定仓库根，再构造参数数组。
**`-f` 必须按 glob 逐个重复**：`adc` 的 `-f` 单次只接受一个文件/glob（见 `adc lint --help`），
`-f a b` 会把第二个当未知参数丢掉——对 `sync` 来说等于"漏掉整个 `sites/**`"，作用域外的站点会被删除。

```powershell
# scripts/lint.ps1（diff.ps1 / validate.ps1 同模式，仅替换命令名与追加 --timeout）
Set-Location "$PSScriptRoot\.."               # 锚定仓库根，避免 cwd 依赖
$files = @(
  "configs/global/**/*.yaml",
  "configs\sites\**\*.yaml"
)
$adcArgs = @()
foreach ($f in $files) { $adcArgs += '-f'; $adcArgs += $f }   # 逐个重复 -f
& .\adc.cmd lint @adcArgs
```

```powershell
# scripts/sync.ps1 — 全量同步（⚠️ 作用域外的资源会被删除）
# 用法：.\scripts\sync.ps1 [-SkipLint] [-Yes]
param([switch]$SkipLint, [switch]$Yes)
Set-Location "$PSScriptRoot\.."
$files = @(
  "configs/global/**/*.yaml",
  "configs\sites\**\*.yaml"
)
$adcArgs = @()
foreach ($f in $files) { $adcArgs += '-f'; $adcArgs += $f }
if (-not $SkipLint) { & .\adc.cmd lint @adcArgs }
& .\adc.cmd diff @adcArgs --timeout 60s
if (-not $Yes) {
  $ans = Read-Host "diff 确认无误？输入 YES 后执行 sync"
  if ($ans -ne 'YES') { Write-Host '已取消'; exit 1 }
}
& .\adc.cmd sync @adcArgs --timeout 60s
```

> **sync 作用域**：glob 由 ADC 内部展开（官方 cli.md 明确支持 `-f "**/*.yaml"`），PowerShell 不会误展开引号内模式。
> 作用域**只含** `configs/global/**` 与 `configs/sites/**` 两个 glob：
> - **严禁**使用 `configs/**/*.yaml` 这类全量 glob——它会把模板目录 `configs/_templates/`（含 `<site-code>` 占位符）也吞进同步。
> - 不要只传单个站点文件（除非配合 `--label-selector` 明确分区），否则作用域外站点会被删。

### 7.3 常用操作速查

| 场景 | 命令 |
| ---- | ---- |
| 改一个站点 | 改 `sites/<code>/service.yaml` → lint → diff → 全量 sync |
| 只处理自己团队的站点 | `sync ... --label-selector owner=team-a`（官方分区方案） |
| 接管存量网关资源 | `adc dump --with-id -o baseline.yaml` → diff 为空后拆入新结构（[resource-ids.md](./official/adc/resource-ids.md)） |
| 回滚 | 恢复旧 YAML → 全量 sync（本地即真相） |
| 盘点某个类型 | `adc dump -o api.yaml --label-selector site_type=api` |
| 灰度发布 | 路由/上游加 `traffic-split` 插件（[traffic-split.md](./official/apisix/plugins/traffic-split.md)） |

## 9. 多环境演进（后续可选）

本仓库当前是**单环境**（`.env` 指向一台网关）。将来要 dev/staging/prod 多环境，推荐按优先级：

1. **一套文件 + 标签 `env:`**：同一仓库、同一文件，用 `--label-selector env=prod` 向不同网关（`--server` 指向不同 Admin API）同步。
   → 缺点：文件里若需要环境差异值，用 `${ENV}` 变量注入（[adc/configuration.md](./official/adc/configuration.md) §Variables）。
2. **目录级拆分**：`configs/environments/{prod,staging}/...` 各一套完整副本，互不干扰、最安全，但会重复维护。
3. **分支级拆分**：Git 分支各管一个环境（本仓库尚未 `git init`，届时建议先建仓）。

## 10. 安全红线（写进 README 的规则）

1. **`sync` 永远全量**（`global/**` + `sites/**`），除非明确用 `--label-selector` 分区。
   **严禁 `configs/**/*.yaml`**——模板目录 `configs/_templates/` 必须在 sync 作用域外。
2. **禁手工改 Admin API / Dashboard**——下次 sync 会被抹掉；一切变更走 YAML。
3. **不要随意改资源名**（改名 = 删旧建新）；确需改名先 `dump --with-id` 保住 ID。
4. **`global_rules` / `plugin_metadata` 改动 = 影响全网关**，需变更评审。
5. **`.env` 含 Token，永不提交**；密钥用 `${ENV}` 注入（见官方 Variables 一节）。
6. 上线前必须 `diff`，看到**无关的 delete 一律停下排查**。

## 11. CI 关卡设计（GitOps 的核心门禁）

> 原则：**自动化把关"写得好不好"，人工把关"要不要上线"**。`sync` 只允许人工在合并后执行，绝不在 CI 里自动跑。

| 阶段 | 检查 | 失败即拦截 |
| ---- | ---- | ---- |
| PR 提交 | `adc lint -f <全量 glob>`（本地 schema 校验） | 拦 |
| PR 提交 | `adc validate -f <全量 glob> --timeout 60s`（后端校验；需 CI runner 能连网关 Admin API） | 拦 |
| PR 提交 | `adc diff -f <全量 glob> --timeout 60s`：**禁止出现无关的 delete**（比对 diff 输出中的 Delete 项） | 拦 |
| 合并后 | 人工执行 `.\scripts\sync.ps1`（或 CI 手动触发 + 审批） | 人工把关 |

落地示例（GitHub Actions 片段，事件：`pull_request`；命令与本地脚本一致，`-f` 逐个重复）：

```yaml
- name: lint
  run: .\adc.cmd lint -f "configs/global/**/*.yaml" -f "configs/sites/**/*.yaml"
- name: validate
  run: .\adc.cmd validate -f "configs/global/**/*.yaml" -f "configs/sites/**/*.yaml" --timeout 60s
- name: diff
  run: .\adc.cmd diff -f "configs/global/**/*.yaml" -f "configs/sites/**/*.yaml" --timeout 60s
```

> 官方出处：[adc/workflow.md](./official/adc/workflow.md)（CI 顺序 lint → validate → diff → sync）、
> [adc/cli.md](./official/adc/cli.md)（`validate` 明确注明适用于 CI）。

## 12. 假设（Assumptions）与不做（Not Doing）

### 12.1 假设（可检验）

| # | 假设 | 检验方式 |
| ---- | ---- | ---- |
| A1 | 单环境：`.env` 指向一台 APISIX 网关；暂不需要 dev/staging/prod 多环境 | 看 `.env` 是否只有一个 `ADC_SERVER` |
| A2 | 后端固定为 `apisix`（非 api7ee），`--gateway-group` 不适用 | `ADC_BACKEND=apisix` |
| A3 | 站点均为 HTTP/HTTPS（含 WebSocket）服务；暂不需要 stream（TCP/UDP）路由 | 站点清单盘点 |
| A4 | 站点规模几十~上百，`sites/` 单层目录足够；超过则按业务域在 `sites/` 下加一层分组 | 站点数统计 |
| A5 | 所有站点资源（service/consumer/ssl）由本仓库全量管理，不存在仓库外的"旁路资源" | `adc dump` 与仓库内容对账 |
| A6 | 存量网关资源（如有）在上线前已按第 8 节接管，或明确接受首次 sync 的预期差异 | 上线前 `dump --with-id` |

### 12.2 不做（Not Doing，含理由）

| 不做 | 理由 |
| ---- | ---- |
| 多环境目录拆分（`configs/environments/...`） | 当前单环境；多环境演进方案见第 9 节，需要时再落地 |
| CI 流水线文件落地 | 仓库尚未接入 VCS（未 `git init`）；先给设计（第 11 节），建仓后落地 |
| 一次性迁移 Dashboard/Admin API 手工创建的所有存量资源 | 全量接管风险高；按第 8 节"逐站接管 + diff 核对"推进 |
| 覆盖 stream（TCP/UDP）路由模板 | 当前站点均为 HTTP(S)/WS；需要时按 `stream_routes` 扩展模板 |
| 插件文档全量镜像 | 只镜像常用插件；新插件按需加入 `download_official_docs.py` |
